# PR 与 Bug 维护流程

## 处理一个补丁

1. **确认来源和适用性**：记录官方 Issue/PR URL、作者、提交 SHA、抓取日期、当时的合并状态。未合并 PR 不等于可直接采用；确认解决的是个人版 .NET 10 WPF 的真实问题。
2. **复现当前问题**：定位控件代码、依赖属性、模板部件、基础样式及 Demo，记录输入、期望和实际结果。能用断言重现的行为保留回归代码；外观问题记录皮肤、DPI、窗口状态及操作步骤。
3. **最小移植**：沿用上游目录与命名，保留提交归属和许可证。此库起点是源码导入，未证明与官方有共同 Git 历史，不能假定所有 PR 可直接 cherry-pick。对比补丁及当前源码后再选择移植方式。
4. **应用支持政策**：移植时去掉低于 .NET 10 的分支；不顺带修改 Avalonia。保留与 Windows、DPI、主题、输入法相关的必要运行判断。
5. **验证真实结果**：构建 WPF 库和 Demo，运行 DLL 冒烟程序及针对该 Bug 的回归。主题修复修改源字典并验证 Theme.xaml 生成结果；新增文件检查 `.projitems` 和主题输入清单。
6. **更新台账并形成独立提交**：一个可独立回退的问题对应一个补丁记录。写清 API/视觉/行为变化、测试结果、未验证项、下游是否升级及回退方法。构建成功不能代替运行验证。

## 同步官方更新

先检查官方真实提交及变化范围，再对照个人台账。官方合入同类修复后，比较最终实现是否等价，避免重复应用；若已经覆盖个人补丁，保留来源记录并以最小差异收敛。

`D:/Develop/HandyControl-master` 当前是没有 `.git` 的本地源码副本。此次基线调查发现个人库原始 `src` 的 1,724 个跟踪文件与该副本逐字节相同；这只能证明本地文件一致，不能据此判断它是官方最新版本或具体 SHA。后续记录应使用可核实的官方提交。

涉及框架行为、第三方组件或 Win32 互操作且存在不确定性时，先核对官方文档/头文件与维护中的实现，将来源链接及决策写入对应补丁记录。不把猜测写成已确认的缺陷。

## 当前优先顺序

- 先保持 .NET 10 WPF 的编译、主题资源、DLL 使用路径稳定。
- 下一轮依据具体 Issue/PR 或项目复现逐项维护；尚无指定候选，不预填“已合并”记录。
- Avalonia、安装器、NuGet/Release 发布及 Visual Studio 历史项目模板分别建立后续任务，不与控件修复混合。

现有上游 Hexo 使用文档中的旧框架说明以及 `extension/visual studio/` 历史模板不代表个人版支持范围。新增项目以[构建与接入](build-and-use.md)为准。
